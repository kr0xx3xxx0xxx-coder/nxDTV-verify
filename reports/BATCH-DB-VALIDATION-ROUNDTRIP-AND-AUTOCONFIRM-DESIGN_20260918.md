작업명 : BATCH-DB-VALIDATION-ROUNDTRIP-AND-AUTOCONFIRM-DESIGN
✅ 작업 완료 - 배치 업로드 왕복검증·자동확정 흐름 조사 및 설계 선택지 제시

## 목적
사용자가 제시한 9컬럼 왕복(roundtrip) 흐름(①업로드 → ②실DB 접속검증 → ③오류행
"오류여부"="오류"+"비고"에 오류내용 기술 후 재다운로드 → ④수정본 재업로드 →
⑤재검증 통과 시 배치번호와 함께 테이블 저장)이 기존 코드와 실제로 어떻게
맞물리는지 조사하고, 사용자가 직접 제기한 의문("오류 없으면 다 저장하는 게
맞는지")에 대한 설계 선택지를 제시한다. 이번 지침은 조사+설계까지만이며
코드 수정은 하지 않았다.

## 현상 (조사 결과, 파일:줄 근거)

### 1) 품질점검이 실제로 DB에 접속해서 확인하는가
결론: 이미 실제 DB 접속 기반 검증이다. 단순 문법/필수값 체크 수준이 아니다.

- 연결 자체 검증(§preflight): `preflight_quality_connections()`
  (services/upload_quality_check_service.py:206-231)가 선택된 모든 Source
  profile + 단일 Target profile 각각에 대해 `_preflight_probe()`
  (:179-194)를 호출한다. `_preflight_probe`는 `db_query_service._fetch_columns_info`
  (:185-187)로 실제 접속 후 information_schema(catalog)를 조회해
  "접속 자체가 되는지 + catalog 조회 권한이 있는지"를 확인한다(더미 테이블
  대상이라 결과는 0행이어도 접속/권한 자체는 검증됨).
  이 preflight 실패 시 `run_quality_check()`는 run 자체를 생성하지 않고 즉시
  중단한다(:422-429, enforce_connections=True가 운영 기본값).
- 원본 테이블 존재 확인: `_check_src_tables()`(routes/batch_route.py, 재사용,
  :622-626에서 호출)가 실제 원본 DB catalog에 질의.
- 원본/목적지 컬럼 존재 확인: `validate_sql_db_objects()`
  (services/db_object_validation_service.py)가 information_schema.columns를
  조회해 SELECT/INSERT 대상 컬럼이 실제로 존재하는지 전수 확인
  (db_object_validation_service.py:316 주석 "원본: information_schema.columns
  조회 → 누락 컬럼 전수 감지(EXPLAIN 대체)").
- EXPLAIN dry-run: 사용자가 조사 항목으로 짚은 "쿼리를 실제 실행은 안 하고
  EXPLAIN만 해보는 것"은 이미 존재한다 — 단, 주 경로가 아니라 catalog 접근이
  실패했을 때만 쓰는 폴백이다(db_object_validation_service.py:453-479,
  `_cmn_source_select_dry_run` 호출). 같은 파일 :15에 "EXPLAIN dry-run은
  플래너가 첫 번째 오류에서 중단하므로 모든 오류 미감지"라는 한계가 이미
  주석으로 명시돼 있어, catalog 조회가 가능한 한 EXPLAIN보다 우선한다.
- 실제 이관 SQL(INSERT ... SELECT ...) 자체를 목적지 DB에 실행하는 일은
  품질점검 어디에도 없다(카탈로그 조회/EXPLAIN만 수행, DML 실행 없음).

→ 추가 구현 필요 범위: 없음. 사용자가 원하는 "실제 DB 접속 검증"과
"EXPLAIN 폴백"이 이미 모두 구현·운영 중이다.

### 2) build_error_excel 컬럼 구성 vs 사용자 제시 9컬럼 형식 호환성
결론: 호환되지 않는 지점이 하나 있다 — "비고" 재활용안이 기존 입력 필드와 충돌한다.

- 기존 시스템 컬럼(오류 안내용, 원본 뒤에 추가): `QUALITY_SYS_COLUMNS =
  ["품질점검 결과","조치상태","오류사항","고객 수정 안내"]`
  (services/upload_quality_check_service.py:1003). `build_error_excel()`
  (:1051-1147)는 원본 워크북을 그대로 복사하고, 이 4개 헤더가 이미 있으면
  재사용(값만 갱신), 없으면 오른쪽 끝에 새로 추가한다(:1114-1128) — 업무
  컬럼 값은 절대 덮어쓰지 않는다(:1130-1137 주석 "업무 셀 값은 덮어쓰지
  않는다").
- 현재 공식 업로드 템플릿(2026-09-18 커밋 e8aa25c4, routes/batch_route.py)은
  8컬럼: 목적지스키마명/목적지테이블명/이관쿼리/원본스키마명/원본테이블명/
  업무담당자/비고/목적지WHERE — 사용자가 제시한 9컬럼(여기에 "오류여부" 1개
  추가된 형태)과 사실상 거의 동일하다.
- "비고"는 이미 실제 업무 입력 필드다: `services/migration_workbook_parser.py`
  `_ALIASES["remark"] = ("비고","note")`(:99), `_LABELS["remark"]="비고"`
  (:288) — 파서가 "비고" 헤더를 실제 데이터 필드(ParsedMigrationRow.remark,
  :39)로 읽어 DB에 저장한다. 즉 이관팀이 자유롭게 적는 진짜 비고란이다.
- 사용자 제안("비고"에 시스템이 오류내용을 기술)은 이 실제 입력 필드와
  충돌한다: 시스템이 "비고" 칸을 오류 문구로 덮어쓰면 (a) 이관팀이 원래
  적어둔 비고 내용이 사라지고, (b) 수정 후 재업로드 시 그 오류 문구가
  파서에 의해 진짜 "비고"(remark) 값으로 그대로 저장돼 버린다(파서는
  "비고" 칸의 의미를 구분하지 못한다 — 값이 무엇이든 remark로 읽는다).
- "오류여부"는 `_ALIASES` 어디에도 없다. 이런 미지정 헤더가 업로드되면
  `_build_field_map()`(:143-157)이 그냥 조용히 건너뛴다(오류도 아니고
  캡처도 안 됨) — 즉 사용자가 "오류여부" 칸에 뭘 적어 올려도 현재 파서는
  그 값을 전혀 읽지 않고 버린다.

→ 정리하면: (기존 4컬럼 시스템 안내 방식) vs (사용자가 원하는 1컬럼
"오류여부"+"비고" 재활용 방식)은 컬럼 개수 철학이 다를 뿐 아니라, 후자는
"비고"의 기존 입력 의미와 실제로 충돌한다. 임의로 코드를 바꿔 "비고"를
오류 문구로 덮어쓰게 하는 것은 이번 지침 범위(조사+설계) 밖이라 실행하지
않았다 — 아래 제안해결안에서 방향만 제시한다.

### 3) 자동확정 vs 별도확인 — 기존 동작 재확인
결론: "품질점검 통과 → 자동 확정"은 완전 자동이 아니다. 이미 사람이 누르는
별도 확인 버튼이 최초 1회 존재하고, 그 이후 재검증에서만 자동으로 재확정된다.
또한 이 "확정"은 목적지 DB에 이관 SQL을 실제 실행하는 것이 아니라, 검증기
내부 SQLite에 "이번 검증 대상 쿼리 목록"을 등록하는 것이다 — 이 구분이
사용자의 우려("DB에 저장")를 이해하는 데 중요하다.

흐름 실체:
  1단계(사람이 누르는 게이트) — "자료 수집 완료" 버튼
    `POST /batch/group-collection-complete`
    (routes/group_upload_view_route.py:90-133). 클릭 시
    `get_collection_summary()`의 `can_confirm` 조건
    (services/upload_quality_check_service.py:1829-1834)을 먼저 확인한다:
      - 미점검 파일 0건, 자체오류 0건, 파일간 중복(조치필요/대기) 0건
      - 전체 이관쿼리 수 == 고유 목적지 테이블 수(목적지 중복 없음)
      - 연결 preflight 증거 보유(품질점검이 실제 DB에 접속해 통과한 run)
    하나라도 어긋나면 400 + `block_reason` 메시지로 버튼 자체가 막힌다
    (:1836-1850). 통과해야만 `finalize_confirmation()`
    (:1951-1988)이 호출돼 run/batch 상태를 "검증대상 확정"으로 바꾸고
    `DTV_mv_group_current_snapshot`에 실제로 행을 저장한다 — 이 INSERT가
    "테이블에 저장"에 해당하는 지점이다.
  2단계(그 이후 자동 재확정) — 한 번 `collection_completed=True`가 세팅된
    뒤에는, 이후 파일을 고쳐 재업로드하고 품질점검을 다시 돌리면
    `_run_quality_check_locked()`(:765-773)이
    `completed and cnt_fix==0 and cnt_pend==0 and cnt_dupwait==0 and
    cnt_norm==len(active) and preflight_passed`를 만족할 때 `confirmed=True`를
    스스로 다시 세팅한다 — 이때는 버튼을 다시 누르지 않는다. 이 부분이
    "자동"이라 부를 수 있는 지점이며, 사용자가 우려한 "그냥 다 저장되는 거
    아니냐"는 정확히 이 재확정 단계를 가리킨 것으로 보인다.
  중요한 구분: 이 확정(스냅샷)은 "메타데이터 수집" 단계의 대상 목록을
    고정하는 것뿐이다(get_metadata_reconciliation() 문서,
    services/upload_quality_check_service.py:1908-1918: "기준=품질확정
    snapshot"). 원본→목적지로 실제 이관 SQL을 실행하는 행위(DML 실행)는
    이 확정과 무관하며 검증 파이프라인 어디에도 포함돼 있지 않다.

## 제안해결안 (사용자 우려 4번에 대한 설계 선택지)

옵션 A. 현행 유지(1단계 수동 게이트 + 2단계 자동 재확정)
  근거: 이미 (a) 사람이 최초 1회 누르는 명시적 버튼, (b) 그 버튼 자체에
  자체오류/중복/미점검/연결preflight 4중 조건, (c) 이번 조사에선 다루지
  않았지만 코드 주석상 확정 소실 방지 3중 락(operation_token +
  BEGIN IMMEDIATE 트랜잭션 재확인 + 부분선택 보호,
  upload_quality_check_service.py:252-259)까지 갖춰져 있다. "재확정"은
  완전히 새로운 대상이 아니라 사람이 이미 승인한 범위 내에서, 정상 재검증
  결과만 반영한다.
  장점: 추가 개발/회귀 위험 없음. 이미 실사용·테스트된 로직.
  단점: 재확정이 자동으로 일어난다는 사실이 화면에 뚜렷이 드러나지 않으면
  사용자가 "내가 안 눌렀는데 언제 확정됐지"라고 느낄 수 있다(신뢰/설명력
  문제이지 안전성 문제는 아님).

옵션 B. 재검증 통과 후에도 매번 "최종 확정" 버튼을 다시 요구
  근거: 2단계 자동 재확정 자체를 없애고, 매 라운드트립마다 1단계와 동일한
  수동 클릭을 강제.
  장점: 왕복마다 사람이 명시적으로 개입한 흔적이 남는다 — 사용자가 원래
  그린 그림에 가장 가깝다.
  단점: (1) 이미 can_confirm 4중 조건을 통과한 뒤에 또 클릭하라는 것이라
  실질적 안전성 향상 대비 클릭 피로만 늘어난다. (2) `collection_completed`
  플래그를 "1회성"이 아니라 "재검증마다 리셋"하는 구조 변경이 필요한데,
  이는 위 3중 락·확정 소실 방지 로직과 얽혀 있어 "1~6단계 완료 모듈 임의
  리팩토링 금지" 원칙상 범위가 작지 않다(별도 승인·설계 필요).

옵션 C. 로직은 안 건드리고 가시성만 보강(A 위에 추가)
  근거: 확정/재확정 로직은 그대로 두되, 자동 재확정이 실제로 언제
  일어났는지(예: "n번째 자동 재확정, 최근 hh:mm")를 화면에 노출해 옵션
  A의 설명력 문제만 보완.
  장점: 기존 락/게이트 구조를 전혀 건드리지 않으면서 사용자 신뢰 문제를
  완화.
  단점: UI 변경이 필요하다(작지만 화면 요소 추가) — "우려 자체가 완전히
  해소됐다"기보다는 사후 확인 수단 제공에 가깝다.

추천안: 옵션 A + C. 이유 — 사용자가 걱정한 "오류 없으면 무조건 다 저장"은
현재 이미 사실이 아니다(최초 1회는 사람이 4중 조건을 통과한 뒤 직접
누른다). 이 안전장치를 그대로 두고 "재확정이 일어났다"는 사실만 화면에
드러내는 C가, 락 구조를 재설계해야 하는 B보다 구조 안정성·회귀 위험 면에서
낫다. 단, "비고" 재활용 충돌(현상 2번)은 옵션과 무관하게 별도로 해결해야
한다 — "비고"는 업무 입력 필드로 그대로 두고, 오류 안내는 기존 4개
시스템 컬럼("오류사항" 등)을 그대로 쓰거나, 사용자가 원하는 단순 표기가
필요하면 "오류여부"를 다섯 번째 시스템 컬럼(Y/N)으로 새로 추가하는 방향을
권장한다(기존 4컬럼 방식과 동일한 "원본 컬럼 비파괴" 원칙 유지).

## 기대효과
- 사용자가 "실제 DB 접속 검증"을 요청했던 부분이 이미 구현·운영 중임을
  코드 근거로 확인해, 중복 개발 없이 다음 단계(코드 변경) 논의를 바로
  시작할 수 있다.
- "비고" 재활용이 기존 입력 필드와 충돌한다는 점을 사전에 밝혀, 실제
  구현 단계에서 업무 데이터 유실(비고 값 덮어쓰기) 사고를 예방한다.
- 자동확정 흐름의 정확한 동작 범위(1회 수동 게이트 + 승인된 범위 내 자동
  재확정, 실제 DML 실행과 무관)를 명확히 해, 사용자의 "다 저장되는 게
  맞는지" 우려에 근거 있는 답을 제공하고 다음 결정(A+C 채택 여부)을
  빠르게 내릴 수 있게 한다.
